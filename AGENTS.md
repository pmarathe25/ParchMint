# ParchMint agent instructions

## Read before working

Read [README.md](README.md), then the [product specification](docs/product/README.md) and [architecture](docs/architecture/architecture.md). For UI work, also read the [UI design index](docs/ui-design/README.md).

The product specification defines observable behavior and v1 scope. The
architecture defines boundaries, ownership, canonical formats, and technology.
The UI design documentation defines presentation where it does not change product
behavior. Future-work material does not add v1 scope.

ParchMint is licensed under GPL-3.0-or-later. Keep dependency and bundled-asset
licenses compatible with that license and preserve their required notices.

## Sequence

The [plans directory](plans/README.md) defines the stage order, scope, and
routing. Follow the dispatched stage page.

## Branches and worktrees

The primary agent owns scope, Git, branches, pull requests, integration,
approvals, and final synthesis. Each stage uses one short-lived branch and one
draft PR.

Run serial work in the primary checkout. Use worktrees only for parallel tasks
with disjoint files, contracts, generated outputs, locks, and CI settings.
Non-UI worktrees skip Git LFS material. Only the primary agent may merge, rebase,
push, switch branches, create or remove worktrees, or change another agent's
branch.

## Tests and review

- The implementation agent changes production code and adds developer tests.
- Before seeing the candidate or implementation reasoning, an independent test
  agent writes a brief requirements-first charter in the draft PR. After
  sealing it, that agent may change tests and fixtures only; production bodies
  are not its expected-behavior oracle.
- A separate read-only validation analyst reviews the integrated code, tests,
  and CI against the applicable product, architecture, and design documents. It
  records pass, fail, blocked, or needs-approval on the PR.
- Preserve independent tests during repairs. Rerun them and validation after a
  repair. Return a disputed test to its author or the primary agent with
  evidence.

The PR summary is the compact stage result: requirements, affected contracts
and ownership, tests and platforms, known gaps, and approvals. Code and tests
are the source of truth. Tests and PR summaries cite the applicable requirement
IDs and design references.

## Material changes

Get product-owner approval before changing a product or UI-design rule,
architecture or technology choice, canonical format, public boundary,
licensing, security, privacy, data safety, accessibility, performance, or
cross-platform requirement. Approval is also required for a development
workflow or application concurrency change with material correctness,
packaging, licensing, security, or privacy effects. After approval, update the
current product specification, architecture, UI design, plan, or instructions
directly. Keep `docs/decisions.md` as a short rationale, not a history of
earlier plans.

## Implementation boundaries

- Keep `iced`, editor engines, desktop runtimes, `git2`, `rusqlite`, and
  operating-system types inside adapters. `parchmint-ui-api` is the public UI
  boundary; `parchmint-ui-iced` implements it.
- Build the rich editor as a custom virtualized `iced` widget. Keep the shared
  session and its stable IDs, transactions, comments, anchors, undo order,
  revisions, and canonical projection under ParchMint control. Private
  `DocumentEngine` implementation types do not leak across ParchMint boundaries.
- Treat HTML or CSS generated by Penpot as design reference material. Production
  UI code uses the maintained tokens, assets, and component rules.
- Access project files through `ProjectRepository`, `CanonicalCodec`, and
  `AtomicWriter`; history through `HistoryStore`; search through `SearchIndex`;
  spelling through `SpellcheckService`; rich editing through `EditorAdapter`;
  and operating-system features through the interfaces in
  `parchmint-platform-api`.
- Keep saved authored content in deterministic project files. Recovery records
  continue protecting unsaved edits until a durable save. Treat caches, indexes,
  spellcheck decorations, and workspace state as the architecture defines.
- Route every project-authoring mutation through
  `ProjectCommandDispatcher`.
- Never block the UI thread on filesystem I/O, Git, SQLite, serialization,
  spellcheck, export, or project-wide analysis.
- Keep the same user-visible capabilities for documents near 250,000 words;
  do not add a size-based mode.
- Treat en-US as the only supported v1 language. Preserve UTF-8 data, but do
  not add v1 IME, multilingual editing, bidirectional-text, screen-reader, or
  formal assistive-technology scope from future extension hooks.

## Routing

Use the routing in the dispatched [stage plan](plans/README.md). Choose the
lowest reliable tier.
Stop and recommend escalation when the work is riskier than that tier. Use
`fast_worker` for noisy builds, large test suites, and other high-volume
validation.
